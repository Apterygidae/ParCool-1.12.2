```

```

Cleanroom 用版本隔离实例目录，所以 `getSuggestedConfigurationFile()` 落在
`versions\1.12.2-Cleanroom\config\` 下。**上一轮「配置文件没生成」的报告，原因是查了错误的目录
（叠加当时跑的还是 P0 的 jar —— 该目录下没有留下任何 `parcool-client.cfg` / `parcool-server.cfg` 的痕迹）。**
Patches 里其它 mod 的配置（`jei` / `dsurround` / `waila` …）也都在同一层，可以对照。

**② Forge 会把分类名里的 `.` 当「嵌套分类」分隔符 —— 结果比预期更好**

我原本以为会写出扁平的 `[Client.Control]`，实际产出的是**两级嵌套**：

```
client {
    other { ... }
    animation { ... }
    stamina { ... }
    control { ... }
    hud { ... }
    modifier { ... }
}
server {
    other { ... }
    modifier { ... }
    control { ... }
}
```

而且分类名被 Forge **归一化为小写**（`Client.Other` → `client.other`）。
这是 `Configuration` 的既有行为，读写两侧都会归一化，所以匹配没有问题。
**效果比单层扁平更好**：客户端设置与服务端策略一眼分开。这一点保留。

**③ 客户端类引用的位置改到了 `ClientProxy`**

上一版把 `ClientInGameCheck` 的注册放在 `EventBusForgeRegistry.registerClient()` 上，
并靠 `@SideOnly(Side.CLIENT)` 让 FML 把该方法整个剥离。
现在改为放在 `ClientProxy.preInit`：

- `EventBusForgeRegistry`（公共类，服务端一定会加载）**不再有任何客户端类的引用**
- 「服务端不加载客户端类」由 `@SidedProxy` 保证 —— 这是硬保证，不依赖运行时剥离行为

两种都是 1.12.2 的既有手段，但后者少一层依赖。**后续客户端专属注册一律走 `ClientProxy`。**

## 二、三个架构性决策

### 1. `RegistryRef<T>` —— 保住 `.get()` 语义

**问题**：上游注册项都是 `RegistryObject<T>`，调用处统一写 `Items.ZIPLINE_ROPE.get()` / `SoundEvents.VAULT.get()`。
1.12.2 没有 `RegistryObject`。如果类型换成裸 `Item` / `SoundEvent`，
**P4（26 个 Action）与 P6（方块/物品/实体）里每一处都要删 `.get()`** —— 几百处无意义改动，
而且很容易在删错的地方留下难查的 bug。

**做法**：`RegistryRef<T> implements Supplier<T>`，只有一个 `set()` + `get()`。
字段声明与上游同形，**调用点一行都不用改**。

**行为约定**：未注册时 `get()` **抛 `IllegalStateException`** 而不是返回 null ——
早暴露比晚暴露好；需要容错时用 `orElse(fallback)`。

### 2. `ParCoolPlatform` —— Aqua API 的唯一收口点

**约定：全工程只有这一个文件出现 `(IPlayerResizeable) player` 强转。**

上游 8 个文件直接调用 `player.isSwimming()` / `getDimensions(Pose)` / `isVisuallyCrawling()`
这类 1.13+ 引擎 API。散落各处改的话会变成 20+ 处强转，将来换依赖方式时改动面无法收敛。

文档里给了完整的**「1.16.5 → Aqua」语义映射表**（类 javadoc 里），P3/P4 直接照表改即可。

顺带提供了 1.13+ 语义的适配实现：
- `isFallFlying()` = `isElytraFlying()` **或** `Pose.FALL_FLYING`
- `isInWaterOrBubble()` = `isInWater()`（「气泡柱」是 1.13 概念，Aqua 的 `bubbleColumns` 默认关闭）
- `isReady(player)` —— 兜住「接口已挂载但 `POSE` 还没初始化」的边界情况

### 3. `ConfigItem<T>` —— 保留抽象层

上游 948 行的 `ParCoolConfig` 里，600+ 处调用点用的都是 `.get()` / `.set()`，全部经由 `Item<T>` 接口。
只要接口不变，把底层从 `ForgeConfigSpec` 换成 `Configuration` 就**不需要动任何调用点**。

与上游的唯一差异（已写进接口 javadoc）：
- `register(...)` 参数从 `ForgeConfigSpec.Builder` → `Configuration`
- `getInternalInstance()` 返回 `Property` 而非 `ConfigValue`（供 P5 的配置 GUI 双向绑定）

## 三、⚠️ 从反编译源码核出来的 1.12.2 API 差异（本次最值钱的部分）

**方法**：RFG 构建时会把 Forge 合并后的 MC 源码反编译到
`build/rfg/minecraft-src/java/`，**可以直接读真源码核对签名**。
这比凭记忆写代码可靠得多 —— 本次一次性避免了 4 个编译错误和 1 个静默失效风险。

### 1. 1.12.2 **没有属性注册表**

```
net/minecraftforge/fml/common/registry/ForgeRegistries.java:45-55
只有 BLOCKS / ITEMS / POTIONS / BIOMES / SOUND_EVENTS / POTION_TYPES /
ENCHANTMENTS / VILLAGER_PROFESSIONS / ENTITIES / RECIPES / DATA_SERIALIZERS
—— 没有 ATTRIBUTES
```

上游的 `DeferredRegister.create(Attribute.class, MOD_ID)` 在 1.12.2 **无对应**。
根因是 1.12.2 的 `IAttribute` 不实现 `IForgeRegistryEntry`。

**采用 Forge 官方的同款做法**（`net/minecraft/entity/player/EntityPlayer.java:103`）：

```java
public static final IAttribute REACH_DISTANCE =
    new RangedAttribute(null, "generic.reachDistance", 5.0D, 0.0D, 1024.0D).setShouldWatch(true);
// EntityPlayer#applyEntityAttributes 里：
this.getAttributeMap().registerAttribute(REACH_DISTANCE);
```

即：属性对象是普通静态字段，**挂到玩家身上靠 `EntityConstructing` 事件**。

### 2. 挂属性的时机是安全的（两处源码核对）

| 事实 | 位置 |
|---|---|
| `Entity.<init>` 末尾 post `EntityConstructing` | `Entity.java:269` |
| `EntityLivingBase.<init>` 第 208 行才调 `applyEntityAttributes()` | `EntityLivingBase.java:205-208` |
| `getAttributeMap()` **懒初始化**（判 null 后 new） | `EntityLivingBase.java:1786-1794` |

→ 我们的处理器先跑，随后 `applyEntityAttributes` 只做 map put、不清空，
所以自定义属性会保留；且**不会 NPE**（懒初始化兜住了「字段初始化尚未执行」的问题）。

### 3. 其余签名差异

| 项 | 1.16.5 写法 | 1.12.2 实际 |
|---|---|---|
| 属性取值 | `attribute.getRegistryName()` 等 | **`IAttribute.getName()`**（不是 `getAttributeUnlocalizedName()`） |
| `setShouldWatch` 返回类型 | — | `BaseAttribute`（`BaseAttribute.java:39`），**不能再链式调用** |
| 继承链 | — | `RangedAttribute extends BaseAttribute implements IAttribute` |
| 效果类的名字 | `Effect` | **`Potion`**（`Effect` 是 1.13+ 才改的名） |
| `Potion` 构造器 | — | **`protected Potion(boolean,int)`**（`Potion.java:63`）→ 必须子类化 |
| 效果的 lang key | — | **`setPotionName(...)` 的字符串就是 lang key**（`PotionEffect.java:156-159` 直接返回 `potion.getName()`，不拼前缀） |
| 配置 min/max | `builder.define(...).setMinValue()` | `Configuration.get(cat,key,int,comment,**min,max**)` 有直接重载（`Configuration.java:322` / `:464`），**用它而不是事后 `setMinValue`** |
| `EntityPlayerSP` 所在包 | `net.minecraft.client.entity.player.ClientPlayerEntity` | **`net.minecraft.client.entity.EntityPlayerSP`** |
| 嵌套类型引用 | — | `ConfigGroup` 是 `ParCoolConfig` 的嵌套枚举，**同包内也要写全限定名** |

### 4. 涉及「同名不同义」的两个陷阱

**① 药水**：上游 `Potions` 注册的是 `net.minecraft.potion.Potion`（含多个 `EffectInstance` 的组合）。
1.12.2 里组合药水的类型是 **`PotionType`**，`Potion` 是「单效果」。
照抄会编译不过，或者更糟 —— 编译过了但语义变成一个只带单效果的状态效果。

**② 注册表**：`ForgeRegistries.POTIONS` 两个版本同名，但语义对应：
1.16 `POTIONS` = `Effect`（效果） ↔ 1.12.2 `POTIONS` = `Potion`（效果）；
1.16 `POTION_TYPES` ↔ 1.12.2 `POTION_TYPES`（组合）。

## 四、顺带修正了上游 2 个**静默失效** bug

逐条核对 `assets/parcool/sounds.json`（19 个键，权威清单）后发现
上游 `api/SoundEvents.java` 有三处对不上：

| 上游写法 | 症状 | 本次修正 |
|---|---|---|
| `SoundEvent` = `parcool:hang_down.jump` | `sounds.json` 里的键是 `action.hang_down.jump` → **该音效永远不响** | `action.hang_down.jump` |
| 注册名 `action.enable`，资源名 `parcool.enable` | 资源名对、注册名不一致（影响 `/playsound` 与注册表可读性） | 统一为 `parcool.enable` |
| 注册名 `action.disable`，资源名 `parcool.disable` | 同上 | 统一为 `parcool.disable` |

**结构上杜绝复发**：`SoundEvents` 里所有音效名只在 `ALL_NAMES` 列一次，
字段与注册都由它派生，并带一条长度一致性断言。`sounds.json` 成为唯一事实来源。

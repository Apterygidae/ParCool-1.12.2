## 一、本轮解开了什么

P3-A 结束时确认了唯一的依赖瓶颈：**所有东西都卡在 `ActionList` + `Action`**。
本轮把整条链一次性建起来：

```
ActionList（动作注册表）
   ↑
Action（状态机基座，3 个抽象方法 + 20 个可覆写钩子）
   ↑
Parkourability（每玩家一份：动作实例 + 计时器 + 强制器 + 信息视图）
   ├── AdditionalProperties（衍生计时器：疾跑/落地/游泳/潜行的连续 tick 数）
   ├── BehaviorEnforcer（行为强制器：取消跳跃/潜行/疾跑/滑翔…）
   └── ActionInfo ─┬── ClientSetting（客户端设置的同步快照）
                   └── ServerLimitation（服务端限制的同步快照）
                          ↑
                    ParCoolConfig 的 per-action 配置（按 simpleName 存键）
```

**这条链现在通了，而且协议层（`writeTo`/`readFrom` 的字节格式）与上游一致 —— P2-B 的四个包可以直接接上去。**

## 三、为什么 `ActionList` 是空的（这是刻意的）

本轮试装了 `Dodge` 作为第一个真实动作，发现**单个动作的依赖面比预期大得多**：

| Dodge 需要 | 属于 |
|---|---|
| `client/animation/impl/DodgeAnimator`、`Animation` capability | **P5** |
| `client/input/KeyBindings`、`KeyRecorder`（双击检测、按键按下） | **P4-B（客户端输入）** |
| `extern/AdditionalMods`（BetterThirdPerson / ShoulderSurfing） | **已决定删除** |
| 自己的一批配置项（`DodgeCoolTime`、`DodgeSpeedModifier`…） | 依赖「有哪些动作」 |

**所以「做一个真实可玩的动作」= P4-B + P5 + 配置 的合并工作量**，不是 P4-A 能顺带完成的。

**本轮的选择**：把**机制**全部建好，让它们**在动作列表为空时也正确工作**，这样后续每个动作都是纯粹的「追加」：
追加一个 Action 类 → 往 `ACTION_REGISTRIES` 加一项 → 加自己的配置项。**不需要再改任何机制。**

空列表是安全的：所有按动作索引的数组长度也为 0，不会越界；`getIndexOf` 对未注册动作返回 -1（与上游一致）。

**配置键用动作 simpleName 而不是索引** —— 所以将来追加动作**不会让已有配置失效**。这是有意的设计。

## 四、⚠️ 修正一条 P1 时的误读：`AdvantageousValue`

**P1 阶段我把 `AdvantageousValue` 写成了一个枚举常量**（配置项）：
```java
// ❌ 我 P1 写的（错误）
AdvantageousValue(ConfigGroup.Other, "Whether server limitations are combined...", "advantageous_value", false),
```

**它其实不是配置项，而是 `Server.Booleans` 每个枚举项上的一个 boolean 字段**：
```java
// ✅ 修正后
public final boolean AdvantageousValue;
// Parkourability 里是字段访问，不是取配置项：
if (server.AdvantageousValue) { return getClientInfo().get(client) && getServerLimitation().get(server); }
```

**为什么会犯**：我当时只看了 `Parkourability` 里 `server.AdvantageousValue` 这一行，见名生意以为是个全局配置项，没有去读 `Server.Booleans` 的字段声明。

**影响面**：`ParCoolConfig` + `StartupChecks`（后者引用了被删掉的常量，编译期就报出来了）。已修，并在 `ParCoolConfig` 里留了修正记录。

**顺带一个待办**：每个 `Booleans` 项的 `AdvantageousValue` 取值我**只对 `AllowInfiniteStamina` 明确给了 `true`**（它必须「客户端想开 + 服务端同意」才生效），其余沿用默认 `false`。**P4-B 时要与上游 `Server.Booleans` 的逐个声明核对** —— 已在字段 javadoc 里标 TODO。

## 五、其余 1.12.2 API 替换（本轮实际遇到）

| 1.16.5 | 1.12.2 |
|---|---|
| `@OnlyIn(Dist.CLIENT)` | **`@SideOnly(Side.CLIENT)`**（加在抽象方法上是合法写法，见下） |
| `PlayerEntity` / `ClientPlayerEntity` | `EntityPlayer` / `EntityPlayerSP` |
| `player.isLocalPlayer()` | `ParCool.PROXY.isLocalPlayer(player)` |
| `player.level.isClientSide()` | `!player.world.isRemote` |
| `Vector3d` | `Vec3d`（方法名一致） |
| `isShiftKeyDown()` | `isSneaking()` |
| `abilities.flying` | `capabilities.isFlying` |
| `isInWaterOrBubble()` | `isInWater()` |
| `LazyOptional.orElse(null)` | `getCapability(cap, null)` 直接返回或 null |
| `INBT` / `Direction` | `NBTBase` / `EnumFacing` |

**关于 `@SideOnly` 加在抽象方法上**：这是 1.12.2 的标准写法。FML 的 SideTransformer 在专用服务端会把标注成员**整个删掉** —— 抽象方法与子类里对应的覆写一起消失，子类仍是具体类，不会变成抽象类。

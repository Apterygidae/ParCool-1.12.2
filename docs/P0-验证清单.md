### 步骤 5 — Aqua 缺失时是否弹出内置依赖界面

Aqua 在 dev 环境是通过 `runtimeOnly files(...)` 上 classpath 的，FML 会从 classpath 里发现它（它 jar 内有 `mcmod.info`）。
**先确认它确实被加载了**：看步骤 3 的自检第 3、4 项是否为 `OK`。

- **若两项都是 OK** → Aqua 已在位。此时做"缺失"实验要**换一种方式**：
  临时注释掉 `build.gradle` 里的 `runtimeOnly files("libs/HydroAgility-1.15.4.jar")`，然后 `./gradlew runClient`。
  > ⚠️ 不要在 Aqua 已上 classpath 的情况下再往 `run/mods/` 复制一份 —— FML 会因为同一个 modid 被加载两次而报重复 mod 错误，那是另一类故障，会掩盖你要验证的东西。
  > 移走时也不要删 `compileOnly`，否则编译会失败。

- **若第 3 项是 FAILED / 第 4 项是 FAILED** → Aqua 没被 FML 发现，此时才需要把 `libs/HydroAgility-1.15.4.jar` 复制到 `run/mods/`（并且**同时**注释掉 `runtimeOnly`，避免重复加载）。

**期望**：游戏不进入主菜单，直接停在 FML 的「缺失依赖」界面，文字形如
「要使用 ParCool!，你必须安装正确的依赖项：要求 aquaacrobatics 1.15.4 或更高版本（缺失）」，
底部两个按钮「打开模组文件夹」「打开latest.log」。

**这一步验证的就是 `@Mod(dependencies = ...)` 字段写对了** —— 界面本身是 FML 自带的，工程里没有任何一行 GUI 代码。

**若游戏正常启动** → 说明依赖声明没被解析，检查：
- 每段是否都以 `;` 结尾
- `required-after` 拼写（不是 `require-after`）
- 版本区间 `[1.15.4,)` 是否与 Aqua 的 `@Mod(version)` = `1.15.4` 匹配得上

### 步骤 6 — 专用服务端能起（验证客户端类没有泄漏到服务端）

#### 它在测什么

1.12.2 的 `@SideOnly` **不是编译期机制** —— 它靠 FML 的 SideTransformer 在**运行期**把标注的成员删掉。
所以只要服务端这一侧哪怕间接引用到某个客户端类，专用服务端启动时就会
`NoClassDefFoundError` / `ClassNotFoundException`。这是**唯一**能在开发期捕获这类泄漏的手段
（单机跑永远发现不了，因为客户端类都在）。

#### 操作步骤

**1. 先确认没有别的程序占用 25565 端口**（比如你正开着的客户端不影响，但别的服务端会冲突）。
若被占用，改 `run/server.properties` 里的 `server-port`。

**2. 第一次运行**（这一步注定会失败，是正常的）：

```bash
cd "D:\installed software\WorkBuddyspace\parcool-backport\ParCool-1.12.2"
./gradlew runServer
```

它会停在类似这样的提示上然后退出：

```
You need to agree to the EULA in order to run the server. Go to eula.txt for more info.
```

同时它在 `ParCool-1.12.2\run\` 下生成了 `eula.txt`。

**3. 同意 EULA**（需自行操作 —— 这是与 Mojang 之间的法律协议，本项目不代为接受）：

用编辑器打开 `ParCool-1.12.2\run\eula.txt`，把

```
eula=false
```

改成

```
eula=true
```

保存。

**4. 再跑一次**：

```bash
./gradlew runServer
```

**5. 等到这一行出现**（大约 10–60 秒，首次会久一点）：

```
[Server thread/INFO]: Done (12.345s)! For help, type "help"
```

**6. 看 ParCool 自检块**（在 `Done` 之前就会打印）：

```
[ParCool] Configuration target: ...\ParCool-1.12.2\run\config\parcool.cfg
[ParCool] Config items registered (client booleans=7, ints=10, doubles=1; server ...)
========== [ParCool] startup self-check ==========
 1. Mixin framework        : OK
 2. ParCool mixin          : PENDING (进入世界后判定)      ← 没人进服，正常
 3. Aqua mixin (interface) : OK (EntityPlayer implements IPlayerResizeable)
 4. aquaacrobatics loaded  : OK
 ...

 7. Potion effect          : OK
 8. PotionType             : OK
10. Config file           : ...\run\config\parcool.cfg (exists=true, ...)
13. Proxy.isActive()      : true
```

> **注意 dev 环境的配置文件在 `ParCool-1.12.2\run\config\` 下**（`runServer` 的工作目录是 `run/`），
> 与你在真实实例里看到的 `versions\1.12.2-Cleanroom\config\` 不是同一份。

**7. 关服**：在**同一个窗口**里直接输入 `stop` 然后回车。

#### 通过标准 / 红旗

| 现象 | 判定 |
|---|---|
| 出现 `Done (...)` 且自检 1/3/4/6/7/8 **都是 OK** | ✅ 通过 |
| `5. patchouli loaded : false` | ✅ 正常（dev 环境没装 Patchouli，它是可选前置） |
| `2. ParCool mixin : PENDING` | ✅ 正常（没有玩家进服，注入点没执行过） |
| 异常里出现 **`net.minecraft.client.`** 或 **`ClientInGameCheck`** / **`ClientProxy`** | ❌ 客户端类泄漏 —— 这是本项唯一要抓的东西，把它贴给我 |
| 启动时就报缺 `aquaacrobatics` | ❌ dev 环境没把 Aqua 当 mod 识别（它在 dev 是靠 `runtimeOnly files('libs/…')` 上 classpath 的） |
| `Address already in use` | 端口冲突，改 `run/server.properties` 的 `server-port` |

#### 当前设计的保障（供理解，不用操作）

「服务端不加载客户端类」现在有**两层**保障：

1. `ClientProxy` 带 `@SideOnly(Side.CLIENT)`，且只由 `@SidedProxy` 实例化 → 服务端根本不会加载它
2. `EventBusForgeRegistry`（服务端必加载的公共类）**已清除掉所有客户端类引用** ——
   原先放在它上面的 `registerClient()` 被移到了 `ClientProxy`

第 2 条是 2026-09-28 的改进：依赖 `@SideOnly` 剥离公共类里的某个方法，需要 FML SideTransformer
在运行期真的把方法删掉才不会解析常量池；而走 `ClientProxy` 是 `@SidedProxy` 的硬保证，少一层依赖。

## 三、⚠️ 1.16 的 `MatrixStack` 在 1.12.2 根本没有对应物

这是本轮最大的一处结构性差异，值得单独说清楚：

| | 1.16.5 | 1.12.2 |
|---|---|---|
| 矩阵模型 | **显式对象** `MatrixStack`（可传递、可入栈出栈、可离屏记录） | **立即模式** `GlStateManager` 维护一份全局矩阵栈，调用即生效 |
| 表现 | `PlayerModelRotator` 持有 `MatrixStack` 字段；`PlayerModelTransformer` 通过 `PlayerModel` 的 `xRot` 等字段操作 | `PlayerModelRotator` 去掉矩阵字段，全部改为直接调 `GlStateManager.translate/rotate` |

### 由此产生的一个 API 缺口（P5 移植 Animator 时必须处理）

- **`PlayerModelRotator.getRawStack()` 在 1.12.2 恒返回 `null`** —— 没有矩阵对象可给。
  **用到它的 Animator 需要改写。**
- 坐标轴常量：上游用 `Vector3f.XN/YN/ZN`，1.12.2 的 MC 没有 `Vector3f`。
  本工程改用 `Vec3d` 并自带 `PlayerModelRotator.AXIS_XN / AXIS_YN / AXIS_ZN`。
  → **P5 移植 Animator 时把 `Vector3f.XN` 机械替换成 `PlayerModelRotator.AXIS_XN` 即可。**

这两处是「Adaptor 改局部、逻辑不动」这个策略**唯一需要动到 Animator 源码的地方**，已记录。

## 四、另外三个「1.16 有、1.12.2 没有」的 API（都在 `PlayerModelTransformer` 里补掉了）

| 1.16.5 | 1.12.2 的处理 |
|---|---|
| `ModelRenderer#copyFrom(other)` | 本类自带 `copyFrom(from, to)`，手动复制 **旋转角 + 旋转基点** 共 6 个字段 —— 正好是 16 版 copyFrom 同步的那一组 |

| `Minecraft.getInstance().getFrameTime()` | `Minecraft.getMinecraft().getRenderPartialTicks()` |

### `bobArms` 的公式来源（已核实，非猜测）

1.16 的 `ModelHelper.bobArms` 本质就是「手臂摆动」，而 1.12.2 的
`ModelBiped.setRotationAngles` 里有完全相同的一段。反编译源码核对结果：

```java
// ParCool-1.12.2/build/rfg/minecraft-src/java/net/minecraft/client/model/ModelBiped.java:260-263
this.bipedRightArm.rotateAngleZ += MathHelper.cos(ageInTicks * 0.09F) * 0.05F + 0.05F;
this.bipedLeftArm.rotateAngleZ  -= MathHelper.cos(ageInTicks * 0.09F) * 0.05F + 0.05F;
this.bipedRightArm.rotateAngleX += MathHelper.sin(ageInTicks * 0.067F) * 0.05F;
this.bipedLeftArm.rotateAngleX  -= MathHelper.sin(ageInTicks * 0.067F) * 0.05F;
```

**系数（0.09 / 0.05 / 0.067 / 0.05）与本类 `bobArms` 逐字一致** ✓

### 字段名对照（同批核实）

```java
// ModelRenderer.java:22-32
public float rotationPointX / rotationPointY / rotationPointZ;
public float rotateAngleX / rotateAngleY / rotateAngleZ;
public boolean showModel;
```

## 七、★ 先把 Aqua 能提供什么摸清了（2026-09-29）

关于「能否借用 Aqua 的 API 省事」，逐项核对源码后 —— **一好一坏**：

### ✓ 好消息：注入点方案成立（已核实源码）

方案里定的「注入打 `ModelPlayer`，天然避开 Aqua 的模型 mixin」**是真的**：

```java
// 1.12.2 ModelPlayer.java:10 / :127 / :129
public class ModelPlayer extends ModelBiped
    public void setRotationAngles(...)                        // :127  ← 自己声明了
    {
        super.setRotationAngles(...);                         // :129  ← 并调用 super
```

`ModelPlayer` 自己声明了 `setRotationAngles`，所以：
- ParCool 注入 **`ModelPlayer.setRotationAngles`**（子类那一层）
- Aqua 的 `@Mixin(ModelBiped.class)` 在 **`ModelBiped.setRotationAngles`**（父类那一层）
- → **两个 mixin 不在同一个方法里，分层隔离** ✓
- → **执行顺序天然正确**：Aqua 在 super 里先改，ParCool 在子类里后改（ParCool 是后手）

### ✗ 坏消息：Aqua 在「模型部位访问」上帮不上忙

我本想复用 Aqua 的 `IModelBipedSwimming` 当模型访问器接口 —— **它只有一个方法**：

```java
public interface IModelBipedSwimming {
    void setSwimAnimation(float swimAnimation);
}
```

Aqua 那些 `@Shadow` 的部位字段（`bipedHead`/`bipedRightArm`/…）**是混入内部的，外部拿不到**。

→ **`PlayerModelTransformer` 必须自己持有 `ModelPlayer` 引用**（它已经这么做了），
这条路省不下来。

### Aqua 的全部客户端渲染注入点（避免冲突用）

| Aqua 的 mixin | 注入点 | 与我们的关系 |
|---|---|---|
| `ModelBipedMixin` | `@Mixin(ModelBiped.class)`；`@Shadow` 6 个部位字段；`@Redirect` 其 `render` 里的 `setRotationAngles` 调用；`@Inject` 其 `setRotationAngles` 的 `swingProgress` 字段处；`@Inject` `copyModelAngles` 调用处 **且 cancel** | **在父类层** —— 我们注入子类，天然隔离 ✓ |
| `RenderPlayerMixin` | `renderRightArm` / `renderLeftArm` 的 `HEAD`；`applyRotations` 的 `TAIL` | 我们**不要去碰这三个点**；`doRender` 是空的，可以安全注入 |

注意 Aqua 在 `ModelBiped.setRotationAngles` 的 `copyModelAngles` 调用（`ModelBiped.java:280`，接近方法末尾）
**直接 cancel** —— 方法尾部被砍掉。我们的注入在子类，不受影响。

### ★ 为什么 `Animation` 的 capability 要单独一个类

上游把 ANIMATION 放在同一个 `Capabilities` 里，只用 `@OnlyIn(Dist.CLIENT)` 标在 `registerClient` 方法上。
**1.12.2 不能这么写**：

1. `@CapabilityInject` 的处理是「按字段的**泛型参数**去查已注册的 capability 并注入」，这个过程需要**按类名加载**该类型；
2. 而 `Animation` 是 `@SideOnly(Side.CLIENT)` 的，在专用服务端上**整个类会被 SideTransformer 剥掉**；
3. → 若把该字段留在公共类 `Capabilities` 里，专用服务端注入时会去加载一个不存在的类。

所以拆到 `ClientCapabilities`（整个类都是 `@SideOnly(CLIENT)`，只由 `ClientProxy` 调用）——
**由 `@SidedProxy` 硬保证服务端不加载它，不依赖运行期剥离**。这与 P2-A 起定下的约定一致。

## 九、P5-B 第二个增量：两个渲染 mixin（已完成）

| 文件 | 目标类 | 注入 |
|---|---|---|
| `mixin/client/ModelPlayerMixin.java` | `ModelPlayer` | `setRotationAngles` 的 `HEAD`（+ `cancellable`）与 `TAIL` |
| `mixin/client/RenderPlayerMixin.java` | `RenderPlayer` | `applyRotations` 的 `HEAD`（+ `cancellable`）与 `TAIL` |

`mixins.parcool.json` 新增 **`client` 数组**承载这两个 mixin。

### ★ 为什么必须放 `client` 数组而不是公共的 `mixins` 数组

这两个 mixin 引用的 `ModelPlayer` / `RenderPlayer` 都是客户端类。
公共数组会在**双端**都尝试应用 → 专用服务端会去加载被 `@SideOnly(CLIENT)` 剥掉的类。
放进 `client` 数组后 Mixin 只在客户端加载它们。

### ★ `applyRotations` 上的让位（与 Aqua 同点共存）

Aqua 的 `RenderPlayerMixin` **也**注入 `applyRotations` 的 `TAIL`（它在那里做泳姿旋转与下移）。
两边都改会把模型转两次，所以本 mixin 的 HEAD/TAIL 都先判：

```java
if (ParCoolPlatform.isReady(player) && ParCoolPlatform.isActuallySwimming(player)) return;   // 交给 Aqua
```

这是移植方案里已定的协调策略。让位判断包在 `try/catch` 里 —— 它是渲染路径上的代码，
不该因为 Aqua 未就绪而把渲染搞崩（出问题就当作「不让位」）。

| `setupRotations(T, MatrixStack, float, float, float)` | `applyRotations(T, float, float, float)` —— **没有 MatrixStack** |

上游 `PlayerModelMixin` 还 `@Shadow` 了 `jacket`/`rightPants`/`rightSleeve`/`leftPants`/`leftSleeve`/`ear`

### ★★ 静态验证：refmap 确认注入目标已解析

`build/tmp/mixins/mixins.parcool.refmap.json`：

```json
"com/alrex/parcool/mixin/client/ModelPlayerMixin": {
    "setRotationAngles": "Lnet/minecraft/client/model/ModelPlayer;func_78087_a(FFFFFFLnet/minecraft/entity/Entity;)V"
```

说明注入点存在、参数表正确。**剩余风险只剩运行时行为，不再是「找不到方法」。**

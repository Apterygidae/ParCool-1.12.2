## ⚠️ 一、为什么 P2 被拆成两步（规划修正）

**做之前先查了 6 个真实消息的依赖，结论是原计划不成立：P2 无法独立完成。**

| 上游消息 | 方向 | 依赖的类 | 属于 |
|---|---|---|---|
| `StartBreakfallMessage` | C→S | `Parkourability` | **P4** |
| `SyncStaminaMessage` | C→S | `IStamina` / `OtherStamina` / `IStamina.Type` | **P3** |
| `SyncServerInfoMessage` | S→C | `ServerLimitation` | **P3** |
| `SyncActionStateMessage` | 双向 | `Parkourability` / `Action` / `ParCoolActionEvent` | **P4** |
| `SyncClientInformationMessage` | C→S | `ClientSetting` / `ServerLimitation` | **P3** |
| `SyncStaminaToClientMessage` | S→C | `IStamina` / `OtherStamina` | **P3** |

**6 个包全部依赖尚未移植的 Capability / Action 类。** 硬做只会写出 6 个编译不过或只能空转的包。

于是拆成：

- **P2-A（本次）**：网络基础设施 + 通道自检。不依赖任何未移植的类，可独立编译与实机验证。
- **P2-B**：Capability / Action 就位后，逐个接入 6 个真实消息（`ByteBuffer` 编解码体可照搬上游）。

**这一节请当作对原移植方案 §5 的修正**：原计划把「网络层」放在 Capability 之前，实际依赖关系是反的。

## 二、P2-A 交付内容

```
common/network/
├── NetworkHandler.java         通道建立 + discriminator 分配表（保留上游编号）+ 注册管线
├── NetworkCheckRequest.java    自检：C→S
└── NetworkCheckResponse.java   自检：S→C
proxy/CommonProxy.java          init() 里调用 NetworkHandler.registerMessages()
client/ClientInGameCheck.java   进世界后发一次自检请求
```

### discriminator 分配表 —— 保留上游编号

```java
ID_BREAKFALL          = 3    // C -> S
ID_STAMINA            = 10   // C -> S
ID_SERVER_INFO        = 12   // S -> C
ID_ACTION_STATE       = 15   // 双向
ID_CLIENT_INFO        = 17   // C -> S
ID_STAMINA_TO_CLIENT  = 18   // S -> C
```

**有意不从 0 连续分配**，而是与 1.16.5 完全一致 —— 移植期间「这个包在对面是几号」不该占用精力。

### 自检为什么用两个类而不是一个类两个 discriminator

`SimpleNetworkWrapper` 内部按 `Map<Class, discriminator>` 分配编号，**同一个消息类注册两次会互相覆盖**，
导致其中一个方向静默失效。要双向就得两个类。这也是 P2-B 接 `SyncActionStateMessage`（双向）时要注意的点。

## 三、⚠️ 1.12.2 网络 API 差异（含踩坑记录）

### 1. `IMessage` 的两个方法参数都是 `ByteBuf`，不是 `PacketBuffer`

```java
// net/minecraftforge/fml/common/network/simpleimpl/IMessage.java（反编译源码原文）
public interface IMessage {
    void fromBytes(ByteBuf buf);
    void toBytes(ByteBuf buf);
}
```

**踩过一次**：写成 `fromBytes(PacketBuffer)` 不构成覆写（`PacketBuffer` 只是 `extends ByteBuf`），
编译报「未覆盖抽象方法 `toBytes(io.netty.buffer.ByteBuf)`」，而且一次会报出 4 条相关错误，不容易一眼看出根因。

**本工程约定**：方法体内包一层 `new PacketBuffer(buf)` 再读写。
这样能用上游那套 `readInt / readBoolean / readString / readBytes / writeString` API，
**P2-B 移植时 encode/decode 体几乎可以照搬上游**（上游方法签名就是 `encode(PacketBuffer)` / `decode(PacketBuffer)`）。

### 2. 其余签名对照

| 项 | 1.16.5 | 1.12.2 |
|---|---|---|
| 通道对象 | `SimpleChannel` | `SimpleNetworkWrapper` |
| 建立通道 | `NetworkRegistry.newSimpleChannel(ResourceLocation, versionSupplier, clientAccepted, serverAccepted)` | `NetworkRegistry.INSTANCE.newSimpleChannel(String name)` |
| 注册消息 | `registerMessage(id, clazz, encoder, decoder, handler)` | `registerMessage(HandlerClass, MessageClass, discriminator, **Side**)` |
| 单/双向 | 一个 handler 内部用 `@OnlyIn(Dist)` 判断侧 | **用 `Side` 参数分流**，同一消息注册两个不同方向的 handler |
| 发全服 | `PacketDistributor.ALL.noArg()` | `INSTANCE.sendToAll(msg)` |
| 发单人 | `PacketDistributor.PLAYER.with(() -> player)` | `INSTANCE.sendTo(msg, entityPlayerMP)` |
| 协议版本校验 | `newSimpleChannel` 的参数 | `@Mod(acceptableRemoteVersions = "*")` + 自己的 limitation 同步机制 |

### 3. 频道名有长度限制

FML 1.12.2 的频道名会被塞进 vanilla 的 custom payload 通道名（`MC\|` 前缀那一套），**有 20 字符上限**。
本工程用 `"parcool"`（7 字符）。上游 1.16.5 用的是 `new ResourceLocation("parcool", "message")`，**这个写法在 1.12.2 无对应**。

## 四、顺带查清的一条：`Can't serialize unregistered packet` 到底什么情况

用户实例里出现过第二账户无法进服：

```
[Server thread/INFO]: Apteryx_a_brider lost connection:
    Internal Exception: io.netty.handler.codec.EncoderException:
    java.io.IOException: Can't serialize unregistered packet
```

**机制**（`NettyPacketEncoder.java:23-45` → `EnumConnectionState.java:308-311`）：

```java
Integer integer = enumconnectionstate.getPacketId(this.direction, p_encode_2_);
if (integer == null) throw new IOException("Can't serialize unregistered packet");
// getPacketId:
return directionMaps.get(direction).inverse().get(packetIn.getClass());   // 精确类名查表
```

三点结论：

1. **是「发送方」序列化失败，不是「接收方没注册」**，包根本没发出去 —— 所以「两个账户实例完全一样」对这个错误没有任何帮助。
2. 查表是「**方向 + 当前连接状态**」两个维度，且是**精确类名**匹配。
3. `registerPacket` 还有两条硬约束（`EnumConnectionState` 文件末尾）：
   - 一个包类**只能属于一个连接状态**，否则抛 `Error: Packet ... is already assigned to protocol ...`
   - 注册时会 `oclass.newInstance()` —— **包类必须有无参构造器**

**候选成因**只剩两类：(a) 某个裸 `Packet` 类没注册到该方向/状态；(b) 某个**已注册**的包在连接状态还没切到 PLAY 时就被发了。

**证据倾向 (b)**：失败恰好发生在 login 完成的那一瞬间，且日志里**没有 `logged in with entity id`**
（第二账户从未真正进服）。状态切换点是 `NetworkDispatcher.java:219/237` 与 `NetHandlerLoginClient.java:110`。

**未能确定的部分（如实说明）**：我试图确认「FML 自己的 `SimpleNetworkWrapper` 包是否会经过 vanilla 的 `NettyPacketEncoder`」，
但没查透 —— `FMLProxyPacket` 在 `EnumConnectionState` 里**没有任何注册**，
而其 `FMLOutboundHandler` 只是 `ctx.write(FMLProxyPacket)` 写进 FML 自己的 embedded channel，
我没找到它转成 vanilla 包的那一步。**所以这一条我保留为未解**，不做断言。

已确认与 ParCool / Aqua 无关：
- **ParCool 零网络代码**（P2-A 之前 `SimpleNetworkWrapper|NetworkRegistry|IMessage|registerMessage|sendTo` 全库零命中）
- **Aqua 只发客户端→服务端**（`NetworkHandler.java:26` 注册的是 `Side.SERVER`，唯一发送点 `ClientProxy.java:97` 的 `sendToServer`）

| `SyncClientInformationMessage` | C→S **+ S→C** | 17 | 上报客户端设置（动作开关/体力消耗/各项配置）；服务端存下并广播 |

### ★ 双向消息必须用**同一个 discriminator**

反编译源码 `FMLIndexedMessageToMessageCodec`：

```java
private final Byte2ObjectMap<Class<? extends A>> discriminators = new Byte2ObjectOpenHashMap<>(); // disc → class
private final Object2ByteMap<Class<? extends A>> types         = new Object2ByteOpenHashMap<>();  // class → disc  ★ 单值
public addDiscriminator(int discriminator, Class<? extends A> type) {
    discriminators.put((byte)discriminator, type);
    types.put(type, (byte)discriminator);          // 同一个类注册两次 → 后者覆盖前者
}
// encodeInto: byte discriminator = types.getByte(clazz);   ← 编码走 class→disc
```

**结论修正**：我 P2-A 时记的「同一消息类注册两次会互相覆盖，双向必须两个类」——
前半句对，但**结论错了**。正确做法是**双向用同一个 discriminator**：
`types` 里只有一个值（一致），`discriminators` 里也只有一个（一致），两边都自洽。

P2-A 的两个自检类当时拆成两个类是可以的，但**不是必需的**。真实消息（`SyncStaminaMessage` /
`SyncClientInformationMessage`）都按「一个类 + 同编号 + 两个 Handler」实现。

### ★ 客户端向 handler 的注册位置

四个消息里，`S→C` 方向的 handler 都是 `@SideOnly(Side.CLIENT)`。
**这些注册语句不能放进 `NetworkHandler`（公共类）**，否则专用服务端会多一层
「依赖 FML 运行期剥离」的风险。所以：

- `NetworkHandler.registerMessages()`（双端）：建通道 + 注册 `C→S` 方向
- `ClientProxy.init()`（`@SideOnly(CLIENT)`，由 `@SidedProxy` 硬保证不加载）：注册 `S→C` 方向

### ★ 1.12.2 的 `ByteBuffer` 载荷写法

上游用 `packet.writeBytes(ByteBuffer)` + `readByte()` 循环读到包尾。1.12.2 的 `PacketBuffer`
没有这个重载，改用 Forge 扩展：

```java
packet.writeByteArray(byte[]);        // 自带长度前缀
byte[] payload = packet.readByteArray();
```
比「读到包尾」更稳（不依赖包内剩余长度）。

### ★ 同步的触发点（让包真正跑起来，而不是死代码）

| 触发 | 位置 | 时机理由 |
|---|---|---|
| 客户端上报设置 + 请求限制 | `ClientInGameCheck`（进世界后首次 tick） | 那时 `mc.player` 已存在 → 连接必然是 PLAY |
| 服务端下发限制 + 体力 | `PlayerJoinHandler`（`PlayerLoggedInEvent`） | 事件在玩家实体加入世界之后触发，连接已是 PLAY |

**这就是「绝不能在 PLAY 之前发包」那条硬约束的落地**：刻意避开
`ServerConnectionFromClientEvent` 这类早期钩子（见第四节里 `Can't serialize unregistered packet` 的机制）。

`SyncStaminaToClientMessage.tick()` 挂在 `TickEvent.ServerTickEvent` 上 —— 它内部的
`TreeMap` 不是线程安全的，上游注释明确要求「只在服务端主线程调用」，事件钩子天然满足。

### P2-B 之后仍未闭环的一环

`SyncStaminaMessage.sync(player)` 目前**没有被周期调用** ——
它应该由 `ActionProcessor`（P4-B）每 tick 调用。也就是说：
**四个包的链路已经通了，但体力值暂时不会周期性上报**（进服时会同步一次）。
这需要 P4-B 的 `ActionProcessor` 来驱动，属于正常顺序。
